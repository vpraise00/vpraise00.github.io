CRONOS: Benchmarking Non-Episodic Reinforcement Learning for Robotic Manipulation

CRONOS는 작업마다 로봇과 물체를 원상복구하는 episodic 강화학습이 아니라, 같은 장면에서 여러 조작 지시를 연달아 수행하는 저빈도 scene-reset 정책 학습을 평가합니다. OpenVLA-7B·SpatialVLA-4B의 PPO 미세조정에서 end-effector reset, 학습 초기 reset curriculum, 휴리스틱 장면 복구를 비교하고, overlap·clutter OOD 성공률과 연속 작업의 실패 누적을 분석합니다.

00 / ONE-MINUTE RECAP

핵심을 먼저 읽기

실험실에서는 매번 물체를 시작 자리로 돌리지만 실제 작업에서는 이전 행동의 결과가 다음 과제의 시작 상태가 됩니다. CRONOS는 이 차이를 VLA 강화학습의 핵심 평가 변수로 만듭니다. (§1–4)

⌁ DEEP TECHNICAL REVIEW연구자용 상세 해설

핵심 경계: CRONOS는 새로운 VLA backbone 제안이 아니라, 이미 학습된 거대 VLA의 강화학습 세팅을 '각 과제별 scene reset'에서 '같은 장면에서 연속 과제'로 바꾸어 평가하는 벤치마크입니다. Table1의 unseen object configurations와 Figure4의 gripper reset, Figure7의 heuristic recovery는 각각 다른 개입을 시험합니다.

01 / 문제 정의

연구가 풀려는 문제

일반적인 로봇 조작 RL은 컵을 집은 뒤 80 step마다 물체와 그리퍼 위치를 초기 상태로 복원합니다. 실제 주방에서 그런 장면 초기화를 매번 사람이 대신 해주면 정책 학습보다 scene reset 비용이 더 커질 수 있습니다. 하나의 공간에서 첫 과제 성공 후 물체 배치가 바뀌고, 두 번째 과제는 그 변화와 이전 그리퍼 끝 위치에서 시작하면 이미 학습한 VLA도 실패를 누적합니다. 기존 non-episodic RL은 상대적으로 작은 정책 위주였고 큰 pretrained VLA를 fine-tune하는 조건이 충분히 검증되지 않았습니다. (§1–2)

02 / 핵심 기여

핵심 아이디어

책상에 사과·컵을 옮기는 지시가 4번 이어지는 상황을 생각해 보겠습니다. 매 지시마다 모든 물체를 시작 위치로 되돌리는 게 episodic T=80입니다. CRONOS의 T=320 설정은 4개 task를 수행한 후에야 장면을 복원하며, T=2560은 32개 task 동안 장면 reset을 줄입니다. 지시가 바뀔 때 그리퍼만 정해진 곳으로 되돌리는 end-effector reset(EER)은 물체를 매번 치우는 것과 다릅니다. 정책은 전 과제의 결과가 남은 상태를 훈련하게 됩니다. (Fig.1, §3–4)

DEEP DIVE / 04

기존 연구와 무엇이 다른가?

Episodic PPO에서는 환경이 모든 reset 때 원래 물체 위치와 그리퍼를 제공하므로 VLA는 비교적 좁은 초기 상태에서 학습합니다. 작은 모델을 scratch 학습한 기존 non-episodic RL 결과를 바로 대형 pretrained VLA에 적용하기도 어렵습니다. CRONOS는 사전학습 VLA에서 scene reset interval이 만드는 state distribution shift를 측정하고, gripper pose correction(EER), 쉬운→어려운 reset curriculum, heuristic scene recovery(HSR)를 각각 ablation으로 평가합니다. 보상 스케일을 높이면 해결된다는 주장과 다릅니다.

03 / 설계와 학습

방법론 · 아키텍처

ManiSkill3/SimplerEnv 기반 물리 시뮬레이터를 확장해 4개 scene, scene마다 물체 2개·receptacle 2개를 두며 조건부 put-object-on-receptacle 지시를 구성해 총 16종 task를 평가합니다. Task switching은 80 steps이고 장면 초기화 간격을 T=80/320/2560으로 조절합니다. OpenVLA-7B 및 SpatialVLA-4B를 PPO+LoRA로 fine-tune하며 동일 장면에 task 지시가 반복해서 주어집니다. EER는 각 task switch 때 로봇 말단 위치만 canonical position으로 복귀시켜 action 초기조건 편향을 줄입니다. 별도 reset curriculum은 처음에는 잦은 scene reset으로 배우다가 간격을 늘리고, HSR은 물체가 테이블 아래로 떨어지거나 접근할 수 없는 경우 회복을 위한 reset을 선택합니다. 단순히 '장면을 절대 재설정하지 않는다'는 시스템이 아닙니다. (§3–4, Appendix B)

DEEP DIVE / 01

모델 구조와 처리 흐름

개념적 처리 순서를 정리한 편집 다이어그램이며 원논문의 그림을 복제한 것은 아닙니다.

  1. 01

    01. Shared-scene manipulation benchmark 생성

    네 가지 scene에 각각 두 object와 두 receptacle을 배치하고 4개의 조건부 put-on 관계를 조합해 16개의 조작 과제를 정의합니다. 한 scene을 여러 과제가 공유하므로 완료한 작업의 물체 배치가 다음 정책 관측으로 남습니다.

    4 scenes × 4 tasks = 16 manipulation tasks
  2. 02

    02. 세 수준의 scene reset interval 비교

    모든 task는 최대 80 environment step. Episodic T=80은 한 task마다 scene reset, non-episodic T=320은 4 tasks마다, T=2560은 32 tasks마다 scene reset합니다. 'non-episodic=영구 무초기화'와 다릅니다.

    T=80 / 320 / 2560 steps per scene reset
  3. 03

    03. Pretrained VLA를 PPO로 후속학습

    OpenVLA-7B와 SpatialVLA-4B를 LoRA로 업데이트하고 64개의 병렬 시뮬레이션 환경을 사용합니다. Appendix B의 예시는 LoRA rank32, 1 PPO epoch, clip0.2, γ=0.99, GAE λ=0.95, 학습 T=320/지시 전환80, optimizer AdamW의 backbone LR1e-4입니다.

    pretrained VLA → PPO + LoRA → closed-loop policy
  4. 04

    04. EER는 scene을 아니라 팔의 위치만 복구

    태스크 전환 시 gripper/end-effector의 pose를 정해진 초기 위치로 되돌리되, 객체·receptacle은 원위치시키지 않습니다. 사전학습 VLA가 주로 보던 고정 end-effector 시작 pose와 현 과제의 실제 입력 분포 차이를 줄입니다. Figure4는 EER 적용 유무 ablation입니다.

    task switch → gripper canonical pose; scene persists
  5. 05

    05. Curriculum 및 HSR로 비정상 장면 회복

    처음에는 잦은 scene reset으로 기본 조작을 학습시키고 점차 reset 간격을 늘립니다. HSR은 물체가 떨어지거나 작업공간 접근이 어려워 학습을 이어가기 힘든 비정상 배치에서 scene reset을 선택합니다. 이 방식은 인공적인 복구 oracle/heuristic을 허용하는 시뮬레이션 설정입니다.

    short-reset curriculum → long-reset rollout; heuristic recovery
DEEP DIVE / 02

핵심 설계·학습 신호 해설

문제는 보상 설계만이 아니라 초기 상태 분포 이동

고정 위치 물체를 향해 집기를 배운 정책이 이어진 작업에서는 이전 조작 때문에 물체가 겹치고 그리퍼가 엉뚱한 쪽을 향한 장면을 봅니다. Rollout을 계속한다고 성능이 자동 상승하지 않으며, state distribution을 바꾸는 장면·gripper reset 정책을 별도로 설계해야 합니다.

읽기 포인트Figure1의 reset 직후 대비 다음 instruction에서 object drift와 success decay를 확인합니다.

EER가 도움 되는 백본과 조건

VLA pretrained policy는 특정 말단 시작 자세에 익숙할 수 있습니다. EER는 scene reset보다 저렴해 보이지만 실제 로봇에선 안전한 경로계획·충돌검사가 필요합니다. Figure4의 SpatialVLA 개선 곡선을 T=320과 T=2560로 나누어 보아야 합니다.

읽기 포인트Figure4에서 +25%p / +10%p는 곡선에서 읽은 대략값이며 논문 표에 보고된 정확한 point estimate와 혼동하지 않습니다.

왜 reset curriculum과 HSR을 별도로 비교하는가?

초기부터 T=2560 같은 매우 긴 rollout을 강요하면 정책이 실수로 작업공간을 훼손한 뒤 유익한 경험을 충분히 모으지 못할 수 있습니다. Curriculum은 초반의 안정적인 성공 경험을 늘리고, HSR은 정상 작업으로 회복 불가능할 때 데이터 낭비를 줄입니다. 두 개입은 서로 다른 실패 메커니즘을 겨냥합니다.

읽기 포인트Fig.5 curriculum, Fig.7 HSR과 EER Fig.4를 한 가지 기법의 성공으로 합산하지 않습니다.

OOD 개선과 장기 sequence 개선을 혼동하지 않기

Table1의 OOD 성공률은 독립 단일 과제 평가이며, 4-task order의 task2 성공률은 연속 수행 지표입니다. 학습에서 reset을 줄였다는 이유만으로 학습하지 않은 길이 32의 성공률이 같은 폭으로 향상된다고 추론할 수 없습니다.

읽기 포인트OOD scene sampling 규칙(Overlap≤12cm, Clutter dropped-from-above)과 rollout length를 기록합니다.

05 / 비판적 해석

한계와 비판적 검토

CRONOS는 실제 로봇 현장학습이 아니라 시뮬레이션 조작 환경입니다. EER의 물리적 이동 비용, HSR의 복구 판단 오류, 실제 그리퍼 재배치 중 발생하는 충돌 위험은 별도 검증이 필요합니다. 평가하는 VLA가 OpenVLA와 SpatialVLA 두 백본에 제한되고, OOD overlap·clutter 정의도 특정 장면 생성기와 물체군에 국한됩니다. 14→64%를 CRONOS의 보편적 학습 성능이라고 일반화해서는 안 됩니다. non-episodic은 'reset 없음'이 아니라 *정해진 더 긴 간격/조건부 reset*을 뜻합니다.

RESEARCH LAB / EDITORIAL PROPOSAL

내 연구에 적용한다면?

아래는 논문 저자의 검증 결과가 아니라, 논문에서 출발해 설계한 **후속 실험 제안**입니다.

검증 가설

동일한 VLA와 PPO 예산에서 scene reset을 덜 자주 하면 미관측 초기 배치 일반화가 개선되지만, EER와 안전한 복구가 없으면 연속과제 종료 성공률이 오히려 낮아질 수 있습니다.

구체적 실험 설계

ManiSkill3에서 4 scenes, 16 task definitions, T80/320/2560과 EER on/off를 3 seeds로 반복합니다. 학습 total 2.9M steps와 평가 target pose·로봇 백본·action step를 일치시키고 unseen overlap/clutter를 완전 분리합니다.

비교군·Ablation

Episodic T80, non-episodic T320 alone, T320+EER, T2560+EER, curriculum with/without EER, T2560+HSR; OpenVLA & SpatialVLA separately; same PPO/LoRA hyperparams.

기록할 지표

Single-task success by OOD category, 4-task & 32-task strict full-sequence completion, task-index performance decay, physical reset count, EER travel distance/collision proxy, GPU interaction efficiency.

실패 해석·주의점

실물 robot의 end-effector pose reset은 안전한 이동/충돌 계획 없이 구현할 수 없고, heuristic HSR이 evaluation scene에 과적합할 수 있습니다. 복구에 드는 시간과 실패 위험까지 보고해야 합니다.
